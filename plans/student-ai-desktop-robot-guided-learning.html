K151 标准版整机采购门禁

现在只做这一阶段：先确认买到的是完整视觉机器人，不拆散购买未经验证的零件组合。

输入官方规格、淘宝商品页、约 850 元参考价
输出K151 标准版的可核对订单候选
核心技术按能力与接口采购
辅助工具官方文档、淘宝商品页、截图

原理门：买的是能力闭环，不只是“机器人外形”

想看到什么

一台设备自身具备相机、麦克风、扬声器、屏幕和两轴动作，电脑以后只承担更重的识别与编排。

根本限制

同名商品可能是标准版整机、遥控版、单独核心板或只有外壳。外形相近不能证明传感器、动作反馈和源码路线相同。

例如只买外壳，即使照片一样，也没有相机和控制板，后面的视觉教程无法执行。
通用原理

用“能力合同”核对采购：输入传感器、输出执行器、通信、供电、资料和恢复方式必须全部满足，再看价格。

本项目的可观察字段是 K151 型号、相机/麦克风/扬声器、反馈舵机、USB-C、官方文档与源码。
迁移关系

以后购买机械臂或无人车，也先列能力合同；这样换品牌时只重查接口，不会被某个平台的商品名限制。

工具说明：淘宝页面负责确认当前店铺、价格、库存和包装；官方文档与源码负责确认技术能力。两者必须交叉核对。商品图好看不能代替技术证据，例如“会动”不等于舵机能返回当前位置。

你现在只做这 4 步

  1. 打开 K151 商品页，暂时不要付款。
  2. 确认标题或规格明确写有 StackChan K151 标准版；不要选 K151-R、单独配件、外壳或其他 CoreS3 套件。
  3. 记录店铺名称、实时价格、是否现货，以及包装清单；参考搜索价约 850 元，但以你登录后看到的页面为准。
  4. 把商品页截图发给 AI，或者直接复制“商品标题 + 所选规格 + 价格 + 包装清单”。
通过证据：截图或订单候选能同时看见 K151 标准版、店铺、实时价格和包装内容。它只能证明“准备买对型号”，不能证明收到的实物正常。
常见失败：页面默认选中更便宜的配件或遥控版。恢复：切换规格后重新核对完整标题和价格；只要详情不清楚就先不付款。
停止点：把截图或四项文字发来，我核对通过后再决定下单并进入到货阶段。
1

开箱、出厂基线与恢复入口

到货后先证明整机原本正常，并确认有返回原厂状态的入口；本阶段不刷自定义程序。

输入K151 实物、随附 USB-C 数据线、Windows 电脑
输出开箱证据、原厂运行基线、USB 识别证据、下载模式证据
核心技术可恢复基线、启动状态与固件边界
辅助工具手机录像、Windows 设备管理器、M5Burner 官方固件列表

原理门：先保留“已知正常”，再允许修改

想得到的结果与根本限制

我们需要一台以后可以反复修改、失败后还能恢复的机器人。但同一个黑屏现象，既可能来自到货硬件故障，也可能来自错误固件；只看黑屏无法区分原因。

例如开箱时相机原本就坏了，如果先刷程序再测试，就无法证明故障发生在收货前还是修改后。
直接办法为何失败

开箱后立刻刷第三方程序，会覆盖最有价值的对照样本，也可能影响退换货判断。只记住“原来能开机”也不够，因为后续需要逐项对照画面、声音、动作和电脑连接。

通用原理与机制

建立“可恢复基线”：先记录原始状态，再验证设备能进入官方接收固件的下载模式，最后保存官方恢复工具中的对应固件入口。修改失败时，先回到这套已知状态，再判断是不是硬件问题。

这和给电脑做系统恢复点相同：恢复点不创造功能，但让后续实验可逆。
可观察中间状态如何产生结果

开箱照片证明型号和到货状态；原厂视频证明未修改时的行为；Windows 端口增减证明 USB 数据通路；长按 RST 约 3 秒出现绿灯并在松开后熄灭，证明设备进入下载模式。四类证据合在一起，才形成后续调试的起点。

换工具后仍成立

以后改用 Arduino、UiFlow2、ESP-IDF，甚至换另一款机器人，“先记录基线 → 确认恢复入口 → 再修改”的顺序都不变。

不看代码也要懂的技术实现流

协作角色

K151 的启动程序选择正常启动或下载模式；出厂固件产生表情、声音与动作；USB-C 负责供电和传输；Windows 显示设备端口；M5Burner 保存并写入官方固件。每一项只解决一段问题，没有任何一个单独等于“恢复系统”。

数据流

电源输入 → ESP32-S3 启动 → 读取机内出厂固件 → 驱动屏幕、音频和舵机。连接底座 USB-C 后，设备身份通过 USB 传给 Windows；进入下载模式后，电脑未来才能把固件字节写入 Flash 存储。

判断流

先查外观：异常就停止；正常才开机。原厂行为异常就保留证据并走售后，不刷机。原厂行为正常再连接底座 USB-C，通过“拔掉时端口消失、插回时端口出现”确认连接。最后长按 RST 约 3 秒，看到绿灯再松开；随后短按 RST 回到正常启动。本轮只验证入口，不执行写入。

运行位置

启动选择、出厂固件和电机限位运行在 K151；端口识别与 M5Burner 运行在 Windows；手机只负责拍摄证据，不参与机器人控制。

交给 AI 的实施合同

AI 只能指导识别端口、核对官方固件和解释观察结果；没有用户明确授权，不得烧录、擦除或修改固件。若到货即异常，必须优先保留退换货条件。

观察与故障定位

外观异常＝物流或装配层；不开机＝供电或硬件层；能开机但电脑无端口＝数据线、USB 口、驱动或下载模式层；有端口但功能异常＝固件或具体硬件层。先找到最早失败的一层，不跨层猜测。

何时才看代码

本阶段不看代码。只有阶段 3 原样编译失败，或设备接口与官方文档不一致时，才打开构建配置、驱动日志或源码定位。

工具边界：随附 USB-C 数据线接到底座接口，负责供电与数据；Windows 设备管理器用端口出现/消失证明电脑看见设备；M5Burner 是 M5Stack 的官方固件工具，搜索 StackChan 并勾选 Only Official 可找到官方固件。它们负责连接与恢复，不负责理解画面、语音或机器人行为。

实物到货后，一次只做这一组动作

  1. 先不开机：拍外包装、型号标签、全部包装内容和机身六面；不要拆壳。
  2. 建立原厂视频：把机器人放在空旷桌面，短按左侧 USB-C 旁的电源键开机；录下完整启动，动作时不要手扶或手掰转动部件。
  3. 确认 USB 数据通路：用随附线连接底座 USB-C与 Windows。打开设备管理器，比较插线前后新增的端口；若名称不确定，就以拔掉消失、插回出现为准。
  4. 只验证下载入口：长按 microSD 卡槽旁的 RST 约 3 秒，看到旁边绿灯后松开；绿灯熄灭表示进入下载模式。随后短按 RST，确认能回到普通启动。
  5. 确认恢复来源但不写入：在 M5Burner 中搜索 StackChan、勾选 Only Official，记录最新官方固件名称与版本截图。本阶段不要点击 Burn。
阶段 1 通过证据：①包装与机身照片；②原厂完整启动视频；③Windows 端口插拔对照；④绿灯下载模式和普通重启结果；⑤M5Burner 官方 StackChan 固件截图。它们证明设备存在可观察、可恢复的基线，但尚未证明相机、麦克风、扬声器和舵机分别完全正常，那属于阶段 2。
安全恢复：到货外观或原厂功能异常时立即停止，不进入烧录；USB 无端口时先换电脑 USB 口并确认使用随附数据线；电机动作时不要手掰，竖直方向保持官方建议的 5°–85°范围。
当前停止点：如果 K151 还没到货，现在不需要安装软件或操作电脑。到货后先只发“外包装 + 型号标签 + 全部配件 + 机身外观”照片，我核对后再带你开机。

逐项验证“看、听、说、动”

把整机演示拆成四条原始通路，避免把硬件错误误判成 AI 错误。

原理门

目标与限制

摄像头显示连续画面，麦克风产生随说话变化的采样，扬声器播放固定测试音。三者共享主控资源，但故障原因不同。

通用原理

复杂系统先做“冒烟测试”：给每个组件最简单的已知输入，观察最直接输出。

例子：相机先看静态色块，不先做人脸识别；扬声器先播放固定音，不先接语言模型。
迁移关系

任何传感器项目都先验证原始信号，再验证模型解释；原始画面都没有时，调模型阈值没有意义。

工具说明：K151 固件里的设备驱动把相机、音频和反馈舵机转换成程序可读写的数据；输入是传感器采样与目标角，输出是图像帧、音量、声音和实际角度。驱动不会判断“人正在挥手”。

验收动作

  1. 看：让相机对准明暗不同物体，确认画面连续变化并记录一张原始帧。
  2. 听：安静和说话各采一次，确认音量或波形明显不同。
  3. 说：播放固定短音，确认扬声器输出清楚。
  4. 动：分别发送小幅左右与俯仰动作，记录目标角和反馈角；俯仰保持 5°–85°，出现卡顿立即停止。
  5. 把四条结果整理为“输入 → 驱动 → 原始数据/动作”的证据表。
通过：相机、麦克风、扬声器和两轴动作各有独立证据；这只证明硬件通路工作，还不能证明语音识别或动作理解正确。
失败：相机异常但音频正常时，只查相机通路、固件日志和连接，不重装语音模型；动作反馈偏差大时先停止并查机械阻挡。
停止：保存四项证据，进入阶段 3。
3

从官方源码烧录，并改一个行为

官方整机只做起点；这一阶段开始证明你能理解、修改和恢复。

原理门

目标与限制

把源码经过编译变成固件，再写入 K151；修改一个安全且肉眼可辨认的行为，例如待机表情或点头节奏。

直接办法为何失败

只下载别人编译好的固件，能运行却看不到“源码 → 编译配置 → 固件 → 设备行为”的因果链，也无法独立修正功能。

通用原理

先固定一个已核验源码版本，原样构建通过，再做单一小改动；每次只改变一个变量，才能知道结果由什么造成。

本教程固定核验过的仓库提交为 b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e。
可观察结果

依赖安装结果、编译日志、固件文件、烧录日志、自定义行为和恢复结果。

工具说明：ESP-IDF 5.5.4 是把 C/C++ 源码编译成 ESP32-S3 固件的开发框架；官方 StackChan 仓库提供项目源码。它们不会替你决定机器人行为，但 AI 可以按你的要求生成和解释小改动。

实施

  1. 在 Windows 安装官方要求的 ESP-IDF 5.5.4，并克隆 M5Stack/StackChan。
  2. 切到已核验提交，先不改代码完成一次原样构建；保存依赖版本和编译成功日志。
  3. 让 AI 只修改一个安全行为，例如改变待机表情或把一次点头拆成更慢的小步；动作仍受官方限位约束。
  4. 烧录后录制“原版与修改版”对比，再使用阶段 1 的恢复入口验证能够退回。
通过：源码原样构建成功，自定义固件呈现唯一可辨认变化，并能恢复；你能指出改动位于输入、状态、策略还是执行层。
失败：原样构建都失败时不改业务代码，先核对 ESP-IDF 版本、子模块和构建日志；烧录后异常则先恢复基线。
停止：保存构建、对比和恢复证据，进入阶段 4。
4

建立自己可替换的本地硬件接口

官方应用可用于对照，但电脑侧 AI 不应只能从单一平台入口控制机器人。

原理门

目标与限制

电脑在局域网内读取机器人相机帧、音频和状态，并发送受限的表情、语音和动作命令。K151 官方源码已核验，但这些本地接口是否完整存在仍需在实物阶段逐项检查。

直接办法为何失败

把视觉模型或语言模型直接写进电机控制代码，会让换模型时连安全动作都重写；只依赖官方云服务又会被账号、网络和接口变化牵制。

通用原理

用“硬件网关”隔开设备与 AI：向上提供稳定的传感器数据和安全命令，向下适配实际固件、舵机和音频。

例如 AI 只能发 look_left:15，网关负责限位、速度和反馈，不能让自由文字直接变成电机角度。
迁移关系

以后换视觉模型只改电脑侧识别器；换机器人只改网关下层，事件与课堂行为仍可复用。

工具说明：官方源码是可修改基础，本地网关是本项目需要补齐的最小连接层。输入是相机/音频/状态和电脑命令，输出是带时间戳的数据与安全动作结果；它不负责理解画面。若官方固件缺少某个接口，AI 先读当前源码，再只补缺口，不重写整套固件。

实施

  1. 先列接口合同：相机抓拍、短音频、设备状态、回中心、受限转向、表情和播放语音。
  2. 逐项检查官方固件已有能力；已有的直接适配，缺失的才增加最小局域网接口。
  3. 电脑先保存一张机器人相机原图和一段短音频，再发送“回中心”和小幅转向。
  4. 所有动作经过白名单、角度限制、速度限制和停止命令；局域网接口不得直接暴露到公网。
  5. 关闭官方 AI 服务后重做测试，证明基础硬件入口仍属于你。
通过：在不依赖官方 AI 服务时，电脑仍能取得机器人自己的图像/音频，并完成安全回中与小幅转向；日志包含命令、限制后目标和反馈结果。
失败：如果只能从官方应用看到画面，说明本地输入接口尚未形成；回到源码检查数据路径，不伪称已经解耦。动作异常立即使用停止或恢复基线。
停止：本地输入与安全输出都通过后，再组合语音和视觉模型。
5

建立可观察的语音闭环

先看清录音、识别、回答和播放四段，不追求最低延迟。

原理门

目标与限制

K151 录音传到电脑，语音变文字，文字进入语言模型，答复再变成声音送回机器人。任一段失败都会表现成“机器人没回答”。

通用原理

用可替换的接口统一语音转文字、语言模型和文字转语音，并用同一会话编号记录四段耗时。

可观察结果：录音文件 → 识别文字 → 答复文字 → 播放开始；例如有文字没声音时，只排查最后两段。
迁移关系

以后换国内服务或本地模型，只替换对应接口；会话、事件路由和机器人动作不变。

工具说明：语音识别把音频变文字，语言模型生成答复，语音合成把文字变声音；K151 本地网关负责收发。每个工具只拥有一段能力，没有任何一个工具单独等于完整机器人。

实施

  1. 先让机器人录一条固定短句并在电脑保存原始音频。
  2. 接入一个中国大陆可稳定使用的语音识别方案，保存识别文字和耗时。
  3. 把文字交给可替换的语言模型，再把答复交给语音合成。
  4. 通过阶段 4 的本地接口把声音送回 K151，播放时记录同一会话编号。
  5. 密钥只放本地环境配置，不写入网页、源码或 Git。
通过：同一次会话能看到原始录音、正确文字、答复文字和机器人扬声器播放，并能指出哪一段最慢。
失败：已有识别文字但没声音，说明录音和识别已经工作，应查语言模型响应、语音合成和播放接口，不重新调麦克风。
停止：保存一条完整会话轨迹，进入阶段 6。
6

机器人相机 → 电脑动作识别

手机和电脑摄像头都不作为正式输入。

原理门

目标与限制

K151 相机帧通过阶段 4 的接口传到电脑，模型输出人体关键点，再由时间规则得到三个动作。设备相机适合近距离姿态 MVP，不适合远距离细节识别。

直接办法为何失败

每帧都发高质量图片会占网络和内存；只看单帧标签会误触。

通用原理

限制帧率与分辨率，保留时间戳；模型输出归一化关键点，规则层跨帧稳定后才生成事件。

诊断链：画面编号 → 33 个关键点 → 候选动作 → 可信程度 → 持续时间 → 稳定事件。
迁移关系

模型可换，但图像传输、时间戳、事件约定和诊断轨迹继续使用。

工具说明：MediaPipe Pose/Gesture 模型接收图像，输出关键点、手势与可信程度；它不负责网络传输、时间稳定或机器人回应。模型包应下载到项目目录，避免每次联网加载。

实施

  1. 复用阶段 4 的 K151 抓拍或低帧率图像接口，先达到稳定的 5–10 帧/秒。
  2. 电脑保存一张机器人相机原图，证明正式输入不是电脑摄像头。
  3. 运行 MediaPipe，显示骨架、候选标签、可信程度和耗时。
  4. 实现举手：手腕高于肩膀持续 600 毫秒；挥手：手腕横向往返；停止：双腕在胸前交叉。
  5. 保存成功与失败样例，判断门槛进入配置文件而非散落代码。
通过：三个动作各连续测试 10 次，误触与漏判有记录；断开机器人相机后电脑模型停止输入，证明没有偷用别的摄像头。
失败：关键点正常但事件跳动，先查稳定时间和规则，不先换模型；帧都不连续则先查传输。
停止：稳定事件通过后才让它控制舵机。
7

把稳定事件组合成语音、表情和动作

模型建议，安全路由决定。

原理门

目标与限制

举手触发点头和问候，挥手触发转向和回应，停止立即取消动作。不同输入可能同时出现，必须解决冲突。

通用原理

事件路由按白名单、优先级、冷却和当前状态决定执行；停止事件优先于所有娱乐动作。

中间结果：candidate_event → policy_decision → motion_plan → execution_result。
迁移关系

换模型、换声音、换舵机时，事件名称和安全策略继续复用。

工具说明：event-router 是你自己的核心，不是第三方成品。输入是稳定事件，输出是有限的语音、表情和动作计划；它不做图像识别，也不允许自由文字变成任意电机命令。

第一版规则

  • raise_hand：点头一次，屏幕微笑，说“我看到你举手了”。
  • wave：头部慢速朝动作方向转 15°，挥手结束后回中心。
  • stop：停止未完成动作、回安全中心、进入 2 秒冷却。
  • 低于门槛或超时：只记录日志，不动作。
通过：三个动作都有正确组合反馈，重复触发不会堆积，停止能中断；日志能解释每次为何执行或拒绝。
失败：动作排队越来越多，说明缺少冷却或取消；不要提高舵机速度掩盖队列问题。
停止：此时已得到可展示 MVP；阶段 8 是可选扩展。
8

可选：下载 Qwen3-VL 理解开放场景

只有基础闭环稳定且电脑资源允许时进入。

原理门

目标与限制

识别“正在读书、画画、组装零件”等无法仅靠固定关键点规则表达的语义。视觉语言模型更灵活，但更慢、更耗资源，也可能产生不确定描述。

通用原理

快速模型负责连续检测和触发，视觉语言模型只在关键帧上低频解释；输出必须限制为结构化候选与证据。

例：{"activity":"reading","confidence":"medium","evidence":["book-shaped object","gaze down"]}。
迁移关系

大模型换代时保留提示结构、输出校验、缓存、超时和 MediaPipe 回退。

工具说明：Qwen3-VL-2B-Instruct 是可下载视觉语言模型，输入图片/视频与提示，输出文字或结构化描述；它不保证事实正确、不保证实时，也不控制执行器。没有足够电脑资源时，本项目仍可用 MediaPipe 完成。

实施边界

  1. 先检查电脑内存/GPU，再决定 Hugging Face、ModelScope 或 OpenAI 兼容本地服务；不把模型塞入 ESP32。
  2. 每 2–5 秒或事件触发时才取关键帧，限制输出标签集合。
  3. 连续两次相同候选且通过规则层后才回应；超时回退到 MediaPipe。
  4. 课堂展示前准备离线固定演示，避免网络或模型加载阻塞。
通过：至少三类开放活动有真实成功/失败样例；模型超时不会冻结语音、表情或停止事件。
失败：电脑推理慢时先降低调用频率和图像尺寸，不牺牲停止事件和舵机安全。
停止：记录硬件环境、模型版本、耗时和错误案例；没有这些证据不能称“理解动作准确”。
9

脱离平台并迁移到不同任务

不再购买第二台机器人，在同一硬件上证明自己掌握的是结构而不是演示程序。

原理门

目标与限制

目标是官方 AI 服务或某个视觉工具不可用时，基础动作仍可由电脑本地事件接口控制，并把原来的挥手回应改造成不同任务。

只重复烧录官方固件，无法证明接口和判断规则属于自己。
通用原理

把感知工具、统一事件、行为策略和执行器分开；替代实现只需满足同一输入输出约定。

例如视觉模型输出统一的“举手”事件，策略再决定是否点头，执行层只负责安全角度。
迁移关系

学习成果是事件约定、安全策略、诊断轨迹和连接层，不是某个模型账号。换服务、换模型或换任务时保留这些成果。

工具说明：本地事件测试器是一个低成本替身，输入与真实视觉模型相同格式的事件，输出给 event-router；它不识别图像，只证明机器人动作链不依赖某个云服务。之后再接入替代视觉适配器。

迁移验收

  1. 保存当前事件格式、动作白名单、限位、测试和诊断日志。
  2. 断开云语音或禁用原视觉供应商，但不破坏原固件；用本地事件测试器触发点头、转向和停止。
  3. 在同一台机器人上新增不同任务：“检测课堂举手持续 1 秒 → 面向学生 → 语音确认 → 5 秒内不重复回应”。
  4. 保留原来的挥手互动，证明新任务通过新增策略完成，而不是复制另一套成品。
  5. 记录替代边界、失败恢复和两种任务的验收证据。
通过：禁用一个外部实现后，本地测试器仍能驱动安全动作；同一事件层同时支持原互动与课堂举手任务。作品状态达到已验收，学习状态达到能迁移。
失败：如果替换视觉输入就必须重写舵机和语音代码，说明模块边界没有形成；先恢复原路线，再把事件格式和适配器边界抽出。不要通过断电、拔带电线路或损坏配置来制造故障。
停止：保存迁移证据与保留成果清单；此时才完成“可迁移创造”，不是在阶段 7 的 MVP 运行时提前毕业。
